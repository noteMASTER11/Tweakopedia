# Детализация диагностики сети и действия с правилами Windows Firewall

## Цель

Итоговые карточки диагностики сети становятся точками входа в подробный разбор
результата. Пользователь открывает карточку целиком, видит все собранные данные
в Fluent-панели и может выполнить уместное действие. В первой итерации действие
добавляется для пользовательских входящих разрешающих правил Windows Firewall:
их можно удалить после явного подтверждения.

## Пользовательский сценарий

1. Наведение подсвечивает границу итоговой карточки и показывает стрелку.
2. Клик по карточке открывает справа панель подробностей.
3. Панель показывает название, статус, итог и полный список деталей.
4. Для Windows Firewall ниже выводится отдельная карточка каждого найденного
   правила: отображаемое имя, внутреннее имя, профиль, программа, служба,
   протокол, порты и адреса, если Windows вернула эти сведения.
5. Кнопка «Удалить правило» открывает подтверждение с точным именем правила.
6. После подтверждения запускается отдельная операция Executor. Во время работы
   кнопка блокируется. Итог отображается внутри панели.
7. После успешного удаления правило помечается удалённым, а интерфейс предлагает
   повторить диагностику для пересчёта общего результата.

У карточек остальных блоков в этой итерации есть полноценная детализация, но
нет изменяющих действий.

## Детальная модель

Каждый объект `checks[]` сохраняет существующие поля и может содержать `items`.
Для Windows Firewall элемент имеет форму:

```json
{
  "key": "{точное внутреннее имя правила}",
  "title": "Отображаемое имя",
  "description": "Описание",
  "profile": "Domain, Private",
  "program": "C:\\Program Files\\Example\\app.exe",
  "service": "Any",
  "protocol": "TCP",
  "local_port": "8080",
  "remote_port": "Any",
  "local_address": "Any",
  "remote_address": "Any"
}
```

Workflow принимает `items` только у блока `firewall`, не более 64 объектов.
Ключ ограничивается 512 символами, остальные строки — 1024 символами. Поля
неизвестного типа и неизвестные поля отбрасываются.

## Удаление правила

В протокол добавляются:

- `SystemToolOperation::RemoveFirewallRule`;
- `SystemToolStage::RemoveNetworkFirewallRule`.

`SystemToolRequest.target` содержит точное внутреннее имя правила. Протокол
принимает непустую строку до 512 символов без NUL, CR и LF. Контроллер разрешает
передать только ключ, который присутствует в последнем структурированном
результате блока Windows Firewall.

Executor использует отдельный `FirewallRuleRemovalWorkflow`:

1. создаёт каталог `Logs/Tools/NetworkDiagnostics/Backups`;
2. экспортирует текущую политику Windows Firewall в `.wfw` через `netsh`;
3. проверяет существование ровно одного правила с указанным внутренним именем;
4. удаляет его через `Remove-NetFirewallRule -Name`;
5. проверяет, что правило больше не находится;
6. возвращает путь резервного файла и точный ключ в `details`.

Сценарий встроен, передаваемый ключ кодируется Base64 и декодируется как данные,
а не вставляется в исполняемый PowerShell-текст. Если экспорт, поиск, удаление
или контрольная проверка не удались, операция завершается ошибкой.

Автоматический импорт `.wfw` не выполняется: импорт заменяет политику целиком и
может затронуть правила, изменившиеся после резервирования.

## Контроллер

`NetworkDiagnosticsController` хранит отдельно состояние диагностики и
состояние действия:

- `actionState`: `idle`, `awaiting_elevation`, `running`, `succeeded`, `failed`;
- `actionMessage`;
- `activeRuleKey`;
- `removedRuleKeys`.

Новая функция `removeFirewallRule(QString key)` проверяет ключ по последнему
результату, блокирует параллельный запуск и отправляет типизированную операцию.
Результат удаления не стирает карточки диагностики. Новый запуск диагностики
очищает состояние действия и список удалённых ключей.

## CLIXML

Перед выполнением сценарий задаёт `$ProgressPreference = 'SilentlyContinue'` и
использует `-OutputFormat Text`. Workflow дополнительно:

- не показывает строки `#< CLIXML` и XML-записи потока Progress;
- находит служебный маркер даже после XML-префикса;
- сохраняет структурированный результат, если маркер оказался встроен в такую
  строку;
- ограничивает незавершённый строковый буфер.

## Проверка

- протокол принимает удаление корректного ключа и отклоняет пустые, слишком
  длинные и управляющие строки;
- workflow удаления использует фиксированный PowerShell и Base64-данные,
  требует резервный экспорт и корректно отображает ошибки процесса;
- диагностика возвращает структурированные элементы правил и восстанавливает
  маркер из CLIXML-строки;
- контроллер не принимает отсутствующий ключ, сохраняет результат диагностики
  во время удаления и отражает успешный/ошибочный итог;
- QML-тесты проверяют клик по карточке, панель, список правил, подтверждение,
  блокировку кнопки и сообщение результата;
- визуальные снимки проверяются при широкой и узкой компоновке.
