# Полный импорт оставшихся твиков: архитектурная спецификация

Дата: 2026-10-09  
Статус: утверждено пользователем  
Проект: Tweakopedia

## 1. Цель

Однократно разобрать все предоставленные пользователем твикеры и документацию
Winaero, добавить в Tweakopedia все самостоятельные пользовательские настройки,
которые можно выразить типизированными операциями, и зафиксировать причины
отклонения остальных кандидатов.

Результат не ограничивается заранее выбранным количеством элементов. Итоговое
число определяется после дедупликации и проверки поведения параметров.

## 2. Источники инвентаризации

- `C:\Users\User\Desktop\Win11Debloat-master`;
- `C:\Users\User\Desktop\Win-Debloat-Tools-main`;
- `C:\Users\User\Desktop\Tweaks scripts (2026..07.12)`;
- `C:\Users\User\Desktop\ViVe-master`;
- ранее предоставленная документация Winaero Tweaker;
- текущий каталог `content/tweaks` как множество уже реализованных объектов.

Исходные проекты используются для обнаружения кандидатов. Значение, диапазон,
поддерживаемые версии Windows и ожидаемое поведение сверяются с локальными ADMX,
документацией Microsoft и документацией соответствующего приложения.

Сведения об источниках не отображаются в пользовательских статьях.

## 3. Граница понятия «всё»

Кандидат добавляется, если он:

1. представляет отдельную понятную пользователю настройку или действие;
2. имеет определяемое исходное состояние;
3. допускает типизированное применение без выполнения произвольного сценария;
4. позволяет проверить результат;
5. имеет известную границу совместимости;
6. не дублирует уже существующий твик или более канонический системный объект.

В полный импорт входят:

- параметры реестра всех нужных типов;
- системная и OEM-информация;
- задачи планировщика;
- параметры BCD;
- параметры схем питания;
- Windows Optional Features и Capabilities;
- файловые настройки с фиксированным назначением;
- AppX и Feature Store через уже существующие механизмы;
- настройки сторонних приложений, если наличие компонента можно определить.

Не входят:

- конфигурация и запуск служб;
- массовые пресеты и пакетные «оптимизаторы»;
- дублирующие способы изменить один результат;
- ремонтные сценарии и восстановление повреждённой Windows;
- очистка журналов, истории, кэшей и пользовательских данных;
- установка стороннего ПО;
- аппаратно-зависимые константы без универсального смысла;
- устаревшие значения, которые поддерживаемые сборки Windows не читают;
- действия, которые можно выполнить только произвольным PowerShell/CMD-кодом.

Отдельная категория «Службы» не создаётся. Изменение `Start`, удаление и
управление состоянием служб отклоняются с причиной `service-management`.

## 4. Аудит кандидатов

Инвентаризация создаёт машиночитаемый файл
`docs/audits/complete-tweak-import.json`. Для каждого нормализованного кандидата
он хранит:

- стабильный технический ключ кандидата;
- класс системного объекта;
- нормализованное расположение;
- решение `accepted`, `duplicate` или `rejected`;
- ID реализованного твика для `accepted` и `duplicate`;
- код причины для `rejected`;
- краткое техническое пояснение.

Manifest является инструментом разработки и не включается в интерфейс. Он
позволяет доказать, что кандидат не был молча пропущен.

Повторяющиеся строки одного сценария объединяются до принятия решения. Количество
присваивается нормализованным объектам, а не совпадениям текста в файлах.

## 5. Типизированные операции

### 5.1 Значения реестра

Единая модель `RegistryValue` поддерживает:

- `REG_DWORD`;
- `REG_QWORD`;
- `REG_SZ`;
- `REG_EXPAND_SZ`;
- `REG_MULTI_SZ`;
- `REG_BINARY`;
- отсутствие значения.

Операции:

- `registry.set_value`;
- `registry.delete_value`.

Определение состояния сравнивает тип и нормализованное содержимое. Снимок
сохраняет существование значения, исходный native type и точные байты. Возврат
восстанавливает их без преобразования; отсутствовавшее значение удаляется.

### 5.2 Ветви реестра

Операции `registry.create_key` и `registry.delete_key` разрешены только для
фиксированного пути из проверенного YAML. Перед удалением Executor сериализует
полное поддерево с типами и байтами значений. Если снимок нельзя получить
полностью, операция не начинается.

### 5.3 Файлы

Операции:

- `file.copy`;
- `file.replace`;
- `file.delete`.

Назначение задаётся определением твика и не редактируется пользователем.
Исходный файл может быть встроенным ресурсом или выбранным пользователем.
Перед запуском Executor пользовательский файл копируется в каталог транзакции,
получает SHA-256 и далее читается только из этого каталога. Существующий файл
назначения сохраняется в `backup`.

### 5.4 Задачи планировщика

Тип `scheduled_task.enabled_state` включает и отключает существующую задачу
через Task Scheduler COM API. Отсутствующая задача означает `unsupported`.
Снимок хранит исходное состояние `Enabled`; создание и удаление задач в этом
импорте не выполняются.

### 5.5 BCD

Тип `bcd.element` работает с фиксированным идентификатором объекта и
whitelist-набором элементов через BCD WMI Provider. Произвольная командная
строка не принимается. Снимок различает отсутствующий элемент и конкретное
исходное значение.

### 5.6 Схемы питания

Тип `power.setting_index` читает и записывает AC/DC index для фиксированных GUID
с помощью PowrProf API. Твик может управлять одним индексом либо согласованной
парой AC/DC. Снимок сохраняет оба фактических значения.

### 5.7 Optional Features и Capabilities

Типы `windows_feature.state` и `windows_capability.state` принимают только имя,
заданное в каталоге. Backend использует фиксированные аргументы системного DISM
без shell-интерпретации. Состояния: включено/установлено, выключено/отсутствует и
неподдерживается. Возврат выполняет обратную типизированную операцию.

### 5.8 Существующие типы

`appx.remove` и `feature.configuration` сохраняют текущую реализацию. Сырые
ViVe-ID без проверенного пользовательского эффекта в каталог не попадают.

## 6. Параметризованные твики

Определение твика может содержать `inputs` следующих типов:

- `text`;
- `integer`;
- `file`;
- `choice`;
- `boolean`.

Для каждого поля задаются подпись, обязательность, длина или диапазон, допустимые
расширения и размер файла. Пользовательские значения могут подставляться только
в payload типизированной операции. Они не могут изменять путь реестра, имя
задачи, идентификатор BCD, executable или путь назначения файла.

Очередь хранит `tweak ID + target state + normalized inputs`. Каноническое тело
плана содержит введённые значения, а для файлов — имя копии внутри транзакции,
размер и SHA-256.

## 7. OEM-информация

В подразделе `devices/metadata` добавляются независимые редакторы:

- производитель;
- модель;
- часы поддержки;
- телефон поддержки;
- URL поддержки;
- логотип OEM.

Текстовые параметры используют `REG_SZ`. Карточка показывает фактическое
значение, поле ввода и кнопку подтверждения редактирования. Логотип выбирается
кнопкой «Выбрать»; принимается BMP с установленным ограничением размера.

Очистка значения является явным состоянием и означает удаление только
соответствующего параметра. Возврат из истории восстанавливает точный исходный
тип и содержимое.

## 8. Интерфейс

`TweakRow` выбирает редактор по декларативной модели:

- два состояния — Fluent toggle;
- несколько фиксированных состояний — dropdown;
- строка или число — поле и кнопка с галочкой;
- файл — поле только для чтения и кнопка «Выбрать»;
- составной параметр — компактная группа соответствующих редакторов.

Редактирование само по себе не меняет Windows. После подтверждения валидное
значение попадает в очередь, карточка получает существующую подсветку, а очередь
показывает конкретные введённые данные и системные объекты.

Клик по свободной области карточки продолжает открывать статью. Элементы ввода
не должны вызывать открытие статьи и не должны терять введённый текст.

Неподдерживаемые твики используют существующий фильтр. Категория скрывается,
если после фильтрации в ней нет элементов.

## 9. Планирование и транзакции

Каждый новый тип проходит общий поток:

1. обнаружение фактического состояния;
2. проверка совместимости и пользовательского ввода;
3. построение канонического плана;
4. повторное обнаружение перед применением;
5. снимок исходного объекта;
6. применение;
7. чтение и проверка результата;
8. возврат уже выполненных операций при первой ошибке;
9. запись подробностей в историю.

Перекрытия определяются по каноническому ключу системного объекта. Два твика не
могут независимо записывать один объект без явно объявленного отношения.

## 10. Контент

Каждый принятый кандидат получает:

- постоянный уникальный ID;
- русское название и краткое описание;
- полную шестичастную статью;
- точную совместимость по Windows 10/11 и минимальной сборке;
- конечные состояния или схему ввода;
- правила обнаружения;
- требование перезапуска;
- уровень вмешательства и обратимость.

Новые категории не создаются, если настройку можно поместить в существующее
дерево. Подкатегории добавляются только при отсутствии подходящего места.

## 11. Проверки

До реализации каждого семейства операций добавляются падающие тесты:

- загрузка и валидация YAML;
- round-trip протокола;
- whitelist полей и отказ от неизвестных типов;
- обнаружение состояния;
- построение плана;
- снимок, применение, проверка и возврат;
- прерывание в середине пакета;
- сохранение параметров очереди и файлового SHA-256.

Контентные тесты проверяют:

- точное множество принятых ID из audit-manifest;
- отсутствие дублей системных объектов;
- соответствие detection и operations;
- существование категорий и состояний;
- полноту статей;
- заявленные границы сборок;
- наличие решения для каждого кандидата manifest.

QML-тесты проверяют текстовый, числовой, файловый и составной редакторы,
добавление параметров в очередь и отображение конкретных изменений.

Финальная проверка включает весь CTest-набор, release-сборку, однофайловую
упаковку и изолированный self-check portable EXE.

## 12. Организация работы и Git

Реализация может выполняться внутренними вертикальными срезами по семействам
операций, но промежуточные коммиты не создаются. После полного аудита,
реализации, тестирования и упаковки исходники, контент, audit-manifest,
спецификация, план и отчёт фиксируются одним итоговым коммитом.

Публикация релиза и push выполняются только по отдельному запросу пользователя.
